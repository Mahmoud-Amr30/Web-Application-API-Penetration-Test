# **Stored Cross-Site Scripting (XSS)**

# **Using DVWA and Burp Suite**

## Practical Web Application Security Assessment Report

Target Application: Damn Vulnerable Web Application (DVWA)

Testing Tool: Burp Suite Community Edition

Environment: 127.0.0.1:4280 (Local Lab)

# **1\. Project Overview**

This report documents a controlled, practical security assessment of the Stored Cross-Site Scripting (XSS) vulnerability found in the "XSS (Stored)" module of Damn Vulnerable Web Application (DVWA). Unlike Reflected XSS, a Stored XSS payload is saved on the server (in this case, inside the application's guestbook database) and is served back to every visitor who later loads the affected page, without the payload needing to appear anywhere in the URL.

The target was hosted locally at 127.0.0.1:4280. All HTTP traffic generated by submitting the guestbook form was intercepted and analyzed using Burp Suite Community Edition's Proxy / HTTP History feature, across the Low, Medium, and High DVWA security levels.

# **2\. Project Objectives**

* Demonstrate how unsanitized guestbook input (Name and Message fields) can be stored and later executed as JavaScript in every visitor's browser.

* Capture and analyze the raw HTTP POST requests and HTTP responses generated by each guestbook submission using Burp Suite.

* Compare how DVWA's Low, Medium, and High security levels handle a classic \<script\> tag payload versus an \<img onerror\> event-handler payload.

* Distinguish genuine payload execution (an observed JavaScript alert) from cases where the payload is merely stored as inert, filtered text.

* Produce a clear, evidence-based academic report that does not assume a result beyond what the screenshots and HTTP traffic actually demonstrate.

# **3\. Tools and Technologies Used**

| Tool / Technology | Purpose |
| :---- | :---- |
| DVWA (Damn Vulnerable Web Application) | Intentionally vulnerable target application hosting the Stored XSS guestbook module |
| Burp Suite Community Edition v2026.8 | Intercepting proxy used to capture, inspect, and replay HTTP requests/responses |
| Chromium-based Browser | Client used to submit guestbook entries and observe rendered results / JavaScript alerts |
| PHP 8.5.11 / Apache 2.4.68 (Debian) | Server-side stack running DVWA, visible in the X-Powered-By and Server response headers |
| HTTP POST Method | Transport mechanism for the vulnerable txtName and mtMessage form fields |
| DVWA Security Level Cookie (security=low/medium/high) | Controls which server-side input filter is applied to the guestbook fields |

# **4\. Testing Methodology**

For each DVWA security level, two payloads were submitted through the guestbook's Name and Message fields, with the Name field consistently set to "Attacker":

* Payload A (script tag): \<script\>alert('Stored XSS')\</script\>

* Payload B (event handler): \<img src=x onerror=alert('XSS')\>

For every submission, three kinds of evidence were collected: (1) the rendered browser output, including whether a JavaScript alert dialog appeared — and, importantly, whether it appeared again on a fresh page load or in a second browser tab, which is the defining trait of Stored XSS, (2) the raw HTTP POST request captured by Burp Suite, including the DVWA security-level cookie, and (3) the raw HTTP response, including the stored guestbook entries as returned in the HTML body. A result was only recorded as "successful execution" when a JavaScript alert was actually observed. An HTTP 200 OK status code was never treated, by itself, as proof that a payload executed, since a filtered, inert payload also returns 200 OK.

# **6\. Security Level Comparison**

The comparison below is based strictly on what was directly observed in the screenshots and the corresponding HTTP traffic. Where the evidence does not allow a firm conclusion, this is stated explicitly rather than assumed.

| Security Level | Script Tag Payload (\<script\>...) | Image onerror Payload (\<img onerror=...\>) | Evidence |
| :---- | :---- | :---- | :---- |
| Low | Executed successfully — alert observed on load, on reload, and in a second tab | Not separately tested at this level | Images 2–7 (browser); Images 8–10 (Burp, security=low) |
| Medium | Blocked / filtered — tags stripped from the stored output; no alert; confirmed in the raw response HTML | Not separately tested at this level | Images 12–13 (filter evidence); Images 14–17 (Burp, security=medium) |
| High | Blocked / filtered — same stripped-tag behavior as Medium; no alert | Blocked / filtered — entire tag removed, message left blank; no alert | Images 19–22 (filter evidence); Images 23–26 (Burp, security=high) |

*Note on payload coverage: the \<img onerror\> vector was only submitted and captured with a confirmed security-level cookie at the High level in this evidence set; no Low-level or Medium-level test of that specific payload was captured with matching Burp evidence, so no claim is made here about how it would have behaved at those two levels.*

*Note on filter strength: unlike a filter that only removes the literal substring "\<script\>" (which can be bypassed by switching to a different tag), the filter observed here at Medium and High removed both the \<script\> tag and the unrelated \<img\> tag, indicating a broader, tag-agnostic stripping approach for the guestbook's Message field at both of those levels.*
